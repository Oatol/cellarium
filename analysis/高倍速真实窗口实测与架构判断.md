# 高倍速真实窗口实测与架构判断

> 实测时间：2026-11-27。对应工作区 HEAD 前状态：v0.46.0，native DLL SHA `BFCF32227328E74120F93D4E42CF8775D3D1E7A72AEA50AC7E5E1722FB4E00D7`。
> 本轮只新增只读诊断工具，未修改模拟主体、GNP1、存档 schema、Agent 契约或五通道场 schema。

> **⚠️ 2026-11-28 测量口径重大更正**：本文所有 `effective` 倍速数字（12× 封顶、12.14× 等）原用 `_process(delta)` 累加墙钟。delta 被渲染 vsync / `Engine.max_fps` 钳制在 16.7ms，60 帧只累计约 1.0s，而外部 Stopwatch 实测进程真实运行 20–32s，**effective 虚高约 20–32×**。基准已改用 OS 单调钟（`Time.get_ticks_usec()`）为墙钟。阶段 A 的定性结论（12× 是 §2.6 规格封顶、carry 双重计数、render_fps 未接线）作为同步路径的机制分析仍成立，但**所有有效倍速绝对值不可再用**；阶段 B3「突破 32×」结论已整体证伪，详见 `阶段B_独立模拟线程方案.md` §10.4 与 CHANGELOG 顶部。真实吞吐以 OS 单调钟口径为准。

## 1. 测量口径

新增工具：

- `tools/HighSpeedPerfBenchmark.gd`
- `tools/HighSpeedPerfBenchmark.tscn`

它实例化真实 `scenes/main.tscn`，保留真实 Vulkan 渲染、真实 `TickCore._process()`、真实 `Main._on_tick_advanced()` 调用链，冻结细胞数并关闭自主分裂，使 1× / 8× / 16× / 32× 在同一细胞规模下可比。

运行命令：

```powershell
$exe="D:\Tools\Godot_v4.7.2\Godot_v4.7.2-stable_win64_console.exe"
$proj="D:\Tools\Godot_v4.7.2\project\cellarium"
& $exe --path $proj res://tools/HighSpeedPerfBenchmark.tscn -- --cells=512 --warmup=12 --frames=60
& $exe --path $proj res://tools/HighSpeedPerfBenchmark.tscn -- --cells=1024 --warmup=12 --frames=60
```

输出落盘到：

```text
C:\Users\安\AppData\Roaming\Godot\app_userdata\cellarium\high_speed_perf_bench.txt
```

统计口径：

- `effective`：模拟推进速度 = `total_ticks / 60 / wall_seconds`；
- `frame_ms`：真实窗口帧间隔；
- `ticks`：每帧实际执行的 tick 数；
- `carry`：`TickCore.carry_ticks`；
- `gt33/gt50/gt100`：帧间隔超过 33 / 50 / 100 ms 的帧数。

`HSPD_TICKWORK` 为辅助埋点，本轮信号顺序下不作为主结论依据；主结论以 frame / ticks / carry 为准。

## 2. 512 细胞实测

| 档位 | 有效倍速 | 帧间隔 avg / p50 / p95 | 每帧 tick avg / max | carry avg / max | >33ms |
|---|---:|---:|---:|---:|---:|
| 1× | 0.98× | 16.67 / 17.22 / 32.97 ms | 0.98 / 2 | 0 / 0 | 2 |
| 8× | 8.13× | 16.55 / 16.67 / 33.33 ms | 8.07 / 12 | 10 / 20 | 3 |
| 16× | **11.98×** | 16.69 / 17.46 / 29.73 ms | 12.00 / 12 | 2938 / 4096 | 0 |
| 32× | **12.14×** | 16.48 / 16.67 / 28.38 ms | 12.00 / 12 | 3987 / 4096 | 0 |

结论：

- 1× 和 8× 基本达到目标倍速；
- 16× / 32× 都只能跑到约 12×；
- 每帧 tick 数被严格钉在 12，正好等于 `MAX_TICKS_PER_FRAME=12`；
- carry 在 16× / 32× 下迅速涨到 4096 上限；
- 帧间隔没有持续爆炸，>50ms / >100ms 均为 0。

## 3. 1024 细胞实测

| 档位 | 有效倍速 | 帧间隔 avg / p50 / p95 | 每帧 tick avg / max | carry avg / max | >33ms |
|---|---:|---:|---:|---:|---:|
| 1× | 1.00× | 16.61 / 19.70 / 20.72 ms | 1.00 / 2 | 0 / 0 | 0 |
| 8× | 7.89× | 16.44 / 16.67 / 31.52 ms | 7.78 / 12 | 10 / 19 | 0 |
| 16× | **12.20×** | 16.40 / 16.67 / 27.78 ms | 12.00 / 12 | 2875 / 4096 | 0 |
| 32× | **12.00×** | 16.67 / 15.00 / 31.05 ms | 12.00 / 12 | 3998 / 4096 | 0 |

结论与 512 细胞一致：

- 细胞规模从 512 翻倍到 1024，高倍速有效倍速没有明显变化；
- 瓶颈不在渲染帧时，也不在这组场景下 CPU 单帧算不过来；
- 瓶颈是调度上限：60fps × 12 tick/frame = 720 tick/s = 12×；
- `should_update_field()` / `get_render_fps()` 未接线会加重设计缺口，但不是本组 16× / 32× 封顶的直接原因。

## 4. 对用户架构判断的回应

用户提出的核心判断是：

1. GPU 目前只做环境场，浪费大量算力；
2. 最重的模拟主体应该放到 GPU；
3. CPU 核心数有限，继续在 CPU 上做 behavior / physics / dev / metabolism / signal 微优化，上限很低；
4. 应该参考 Alien 的独立模拟线程。

本轮实测后的分层判断：

### 4.1 用户判断成立的部分

- 过去 v0.43–v0.46 主要是在 CPU / native 上抠单 tick，收益已经明显递减；
- 当前 GPU 确实只承担场扩散与场采样，细胞级模拟主体没有 GPU 化；
- 仅靠继续微优化单 tick，不能解决 16× / 32× 调度与高负载场景的长期上限；
- Alien 的独立 worker + CUDA Graph + GPU 常驻状态，确实代表另一条架构路线。

### 4.2 实测揭示的第一因

当前高倍速“体感问题”的第一因不是 GPU 回传，也不是渲染，而是：

```text
MAX_TICKS_PER_FRAME=12
+ carry 只累加不消费
+ 32× 声明的 render_fps=30 / field_interval=4 没有消费端
```

因此在 60fps 下，无论请求 16× 还是 32×，实际都封顶在 12×，carry 堆到 4096。

这是**调度架构问题**，与用户持续的“高倍速卡顿”感受一致；但它比“把全部模拟搬 GPU”更先暴露，也更先可修。

### 4.3 GPU 主体化的现实边界

把 behavior / physics / metabolism / dev / signal 全部搬 GPU，理论上有很大算力空间，但不是局部改造：

- 细胞状态、邻接关系、谱系、账本、RNG、分裂/死亡都涉及状态写入；
- 当前 state hash / 存档 / 回放依赖 CPU 侧确定性顺序；
- GDScript `float` 是 double，`PackedFloat32Array` 是 float32，已有多次 1 ULP 差异教训；
- C++ 原生 hot path 已经用 float32 舍入顺序换来了逐位 hash 稳定；
- 一旦状态主体留 GPU，CPU 只剩命令与 UI，hash / 快照 / 地形笔刷 / Agent 查询都要重新设计回传点。

所以 GPU 主体化是正确方向之一，但应作为架构级版本，而不是在 v0.46 基础上“顺手下沉”。

## 5. 建议分阶段路线

### 阶段 A：先修高倍速调度（已实施）

原目标：先让用户请求的 16× / 32× 不再被 12× 硬顶和 carry 积压吞掉。

**规格边界核查后的修正目标**：§2.6 冻结规格白纸黑字写 16× / 32× 每渲染帧目标就是 12 tick（余量结转），T11 硬断言单帧 ≤12，因此 12× 封顶是**设计使然、不是 bug**。阶段 A 真正能修的是 carry 计数错误与渲染锁帧未接线，不碰冻结规格。

已实施改动：

1. `TickCore._process()` 修复 carry 双重计数——旧实现把 `overflow` 加进 `carry_ticks` 的同时又在 `_accumulator` 留了一份整数余量，导致 carry 二次增长瞬间顶 4096；新实现让 `_accumulator` 只保留不足 1 tick 的小数余量，整数部分全部并入唯一的 carry 欠账来源，下一帧优先消化；
2. `Main._on_speed_changed_render()` 接上 `speed_changed`，按 `get_render_fps()` 设置 `Engine.max_fps` 与 `ProjectSettings run/max_fps`，32× 渲染锁 30 fps（放在 Main 而非 TickCore，避免无头 SmokeTest 创建裸 TickCore 污染全局 Engine 状态）；
3. **未做**：自适应 budget——实测 512/1024 细胞下每帧 tick 总成本约 7 ms、帧 p95 < 33 ms，无收益且会引入抖动，放弃；
4. **未做**：放宽单帧上限到 24——原型实测虽能把 32× 有效倍速从 12.15× 抬到 12.69×，但直接违反 §2.6 冻结规格与 T11 断言，已回退；
5. **未做**：`should_update_field()` 接线——改变模拟语义与 state hash，需重建黄金基线，留待用户拍板。

**阶段 A 后实测（1024 细胞，同会话，12 帧预热 + 60 帧采样）**：

| 档位 | 有效倍速 | carry avg / max（前 → 后） | >33ms 帧 |
|---|---:|---:|---:|
| 1× | 1.01× | 0 / 0 → 0 / 0 | 0 |
| 8× | 8.03× | 9.9 / 19 → 0.3 / 4 | 2 |
| 16× | 12.13× | 2875 / **4096** → 176.7 / **294** | 0 |
| 32× | 12.15× | 3998 / **4096** → 873.4 / **1456** | 0 |

闸门：双工程 SmokeTest `SCRIPTS=72 FAILURES=0`、T11 通过、NativeParityProbe `OK (failures=0)`、state hash 全 match。

结论：carry 不再瞬间顶 4096，HUD 落后提示可按梯度反映真实欠账；有效倍速仍 12×（符合 §2.6 规格封顶）；渲染锁帧已接线。真正突破 12× 需要阶段 B 的架构改动或修订 §2.6 单帧上限，不属于阶段 A 范围。

### 阶段 B：Alien 式独立模拟线程（中高风险，中收益）

目标：让主线程只负责渲染与输入，模拟在独立 worker 中固定 tick 推进。

可行前提：

- 模拟状态必须从 Godot Node 中进一步隔离成纯数据对象；
- worker 线程不得直接调用 Godot Node API；
- CommandBus 作为唯一跨线程入口；
- 主线程读取双缓冲快照渲染，不直接读模拟可变状态；
- state hash 仍按 tick 序列计算，与渲染帧解耦。

收益：

- 明显改善“主线程被 tick 卡住”的体感卡顿；
- 高倍速时渲染可以保持平滑；
- 为后续 CPU 多核分片 / GPU 常驻状态打基础。

风险：

- 线程同步、快照一致性、命令时序、存档时点都要重新定义；
- 当前 `Main._on_tick_advanced()` 依赖 Node 调用，不能原样搬进线程；
- 不增加单 tick 算力，只是解耦响应性。

### 阶段 C：CPU 多核并行化（中高风险，中收益）

目标：利用现有多核，不是临时 `WorkerThreadPool.add_task()` + `wait_for_task_completion()`，而是稳定的按 cell chunk 并行与确定性归约。

可优先对象：

- behavior 输入采集 / 神经评估；
- metabolism 分组；
- 局部碰撞邻域遍历；
- signal 源聚合。

约束：

- 每阶段必须固定归约顺序；
- 不能改变 float32 写入顺序；
- 仍以逐位 state hash 为闸门。

### 阶段 D：GPU 主体化（高风险，高收益）

目标：参考 Alien，把细胞级热路径变为 GPU compute，状态尽量常驻 GPU。

这不是下一小版本能完成的改动，建议先做架构验证：

- 选一个纯函数型阶段（如场采样或小范围邻域统计）做 GPU 常驻原型；
- 验证 CPU 不再读完整状态时的可调试性；
- 验证 hash / 快照 / 存档的新契约；
- 再决定是否迁移 behavior / physics / metabolism。

## 6. 当前建议

不要否定 CPU 微优化的历史价值：它们把裸 tick 从 10ms 以上压到 8ms 内，并把状态逐位一致性保住了。

但用户指出的方向也成立：**下一阶段不应继续在单 tick 上抠最后一个 0.1ms，而应转向调度架构与模拟/渲染解耦。**

推荐顺序：

1. 先做阶段 A，解决 16× / 32× 被 12× 封顶和 carry 积压；
2. 同步做阶段 B 的架构预研，目标是 Alien 式独立模拟线程；
3. 只有在阶段 B 的快照边界稳定后，再评估阶段 C / D；
4. 不直接跳到 GPU 主体化，否则确定性体系、存档、回放和 Agent 查询都会被同时推翻。
