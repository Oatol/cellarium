## 1. 方向一：高倍速真实体感

### 1.1 现状（已核对源码）

倍速机制在 `scripts/core/tick/TickCore.gd` 实现，与规格 §4.3 / 技术文档 §2.6 一致：

| 档位 | speed | 神经间隔 | 场间隔 | 渲染锁帧 | LOD |
| --- | --- | --- | --- | --- | --- |
| 暂停 | 0× | 1 | 1 | 0（不锁） | 0 |
| 1× / 3× | 1 / 3 | 1 | 1 | 0 | 0（全精度） |
| 8× | 8 | 2 | 1 | 0 | 1 |
| 16× | 16 | 4 | 2 | 0 | 2 |
| 32× | 32 | 8 | 4 | 30 fps | 3 |

- 固定 `TICK_DT=1/60`，倍速只改每帧 tick 数、**绝不缩放 dt**；单帧上限 `MAX_TICKS_PER_FRAME=12`，余量进 `carry_ticks` 结转（`TickCore._process()`）。
- 神经 LOD 消费端已接：`OrganismManager.gd:354` 的 `should_update_neural()`；渲染降级已接：`PostprocessLayer.gd:53`（LOD≥2 关后处理）。
- SmokeTest T11 已断言全部档位值、carry、12 tick 上限、单步、dt 不缩放（`tools/SmokeTest.gd:1997`），**测试通过**。

### 1.2 已确认的三个"声明未接线"缺口

1. **场降频无消费端**：`TickCore.should_update_field()` / `get_field_interval()` 全项目仅定义、无调用；`Main.gd:121` 的 `advance_field_tick()` 每 tick 都跑。档位表声明的 16× field=2 / 32× field=4 **实际未生效**。
2. **渲染锁帧无消费端**：`TickCore.get_render_fps()` 无调用；`CellBatchRenderer.gd:39` 注释写"上层可设 Engine.max_fps"，但没有代码真的设置。32× 的 30 fps 锁**实际未生效**。
3. **carry 只记录不消费**：`carry_ticks` 在 `_process()` 里累加并发信号，但下一帧没有"优先消化 carry"的逻辑——注释声称"下一帧优先消化"，实际每帧仍按 `delta*speed` 重新算 budget。32× 持续运行会积压到上限 4096。

### 1.3 关键判断：先测量，别先改

**tick3 的 ~30 ms 是 3×9.4–9.7 ms 串行的必然结果，不是额外开销**（WindowPerfBenchmark 五相位已确认）。它本身不构成 bug。真正要回答的问题是：

> 在 8× / 16× / 32× 档位下，用户实际看到的帧率与模拟推进速率是多少？掉帧来自 tick 累积、渲染、还是场扩散？

现有探针只测 1× 帧成本（`RealWorldTpsProbe.gd`，headless CPU 下界），**没有高倍速档位的真实测量**。因此第一步必须是测量，不是优化。

### 1.4 执行步骤

**步骤 1（只读测量，已完成）**

新增 `tools/HighSpeedPerfBenchmark.gd/.tscn`，在真实 Vulkan 窗口跑真实 `main.tscn` tick 链，固定 512 / 1024 细胞，分别测 1× / 8× / 16× / 32×，每档 12 帧预热 + 60 帧采样，读数落盘到 `user://high_speed_perf_bench.txt`。完整数据与架构判断见 `analysis/高倍速真实窗口实测与架构判断.md`。

实测结论：

- 512 细胞：1× = 0.98×，8× = 8.13×，16× = **11.98×**，32× = **12.14×**；16× / 32× carry 均涨到 4096。
- 1024 细胞：1× = 1.00×，8× = 7.89×，16× = **12.20×**，32× = **12.00×**；16× / 32× carry 均涨到 4096。
- 帧间隔没有持续超过 33 ms，>50ms / >100ms 帧数均为 0；每帧 tick 数被钉在 `MAX_TICKS_PER_FRAME=12`。

因此高倍速体感问题的第一因是**调度上限 + carry 双重计数 + render_fps/field_interval 未接线**，不是 GPU 回传，也不是当前规模下的渲染帧时。

**步骤 2（已完成，阶段 A）**
- ✅ **carry 双重计数已修**：`_accumulator` 只保留小数余量，整数部分并入唯一欠账来源，下一帧优先消化。1024 细胞 carry max 16× 4096→294、32× 4096→1456；有效倍速仍 12×（符合 §2.6 规格），SmokeTest 72/0 + T11 + NativeParityProbe 全过，hash 不变。
- ✅ **32× render_fps=30 已接**：`Main._on_speed_changed_render()` 同步 `Engine.max_fps` 与 `ProjectSettings run/max_fps`；只读诊断确认 32× 档 `engine_max_fps=30`。
- ❌ **自适应 budget 放弃**：实测每帧 tick 成本约 7 ms、帧 p95 < 33 ms，无收益且引入抖动。
- ❌ **放宽单帧上限放弃**：原型 24 tick/frame 虽把 32× 有效倍速抬到 12.69×，但违反 §2.6 冻结规格与 T11 断言，已回退。
- ⏳ **场降频未接**：`should_update_field()` 是玩法变更，改变 state hash，需重建黄金基线并用户拍板，不属阶段 A。

**步骤 3（风险边界）**
- ❌ 不改 `neural_interval` 的既有语义（改了就变 hash，且神经是玩法核心）。
- ❌ 不碰已通过的裸 tick 口径与 ≤8 ms 验收基线。
- ❌ 不动 `MAX_TICKS_PER_FRAME=12` 的规格约束（要改先修订 v1.0 / §2.6）。
- ✅ 允许：接线已有声明（render_fps / field interval）、调度策略优化、表现层降级。
- 每步仍走固定流程：先测后改 → 同会话 A/B → 双工程 SmokeTest + NativeParityProbe + flat parity → 如实记录 → 文档同步 → tag + push。

## 2. 方向二：玩法完成度收尾

### 2.1 验收基准与现状

以 `docs/Godot项目技术设计文档.md` §10「开发里程碑与验收标准」的六阶段 DoD 为基准（玩法以 v1.1 合并稿为准）。核对结论：

| 阶段 | DoD 关键项 | 覆盖情况 |
| --- | --- | --- |
| 1 基础沙盒 | 圆形皿、单细胞进食/运动/分裂/死亡、营养温度场、4 性状编辑器、种群统计 | 已落地；T11 档位 1×/3×/8× 可用 |
| 2 多细胞发育 | 发育式基因组、受精卵→成熟、10 种功能细胞、弹性连接、GenomeCodec `.gnm` 冻结、守恒断言 | 已落地（v0.14–v0.29）；§5.3.6 单细胞个体/发育深度轴已实现 |
| 3 神经与行为 | 细胞级神经、感知-决策-运动、觅食/避障/捕食、呼吸效率、同种子哈希一致 | 已落地；§5.4.1 DIVIDE/REPRODUCE 走 CommandBus 分离 |

### 2.2 已确认的缺口清单（按优先级）

**P0 — 具体 bug，低风险高价值**
1. **`gene.set_trait` / `gene.set_respiration` 命令名不匹配导致接口落空**。`scripts/agent/AgentBridge.gd:178-180` 用 `command_name.to_upper()` 生成 type → `GENE.SET_TRAIT`（带点）；而 `OrganismManager.gd:62/1756` 的执行器期望 `GENE_SET_TRAIT`（带下划线）。两条基因编辑接口入队后无人消费，**17 上游接口实际只有 15 条可用**。SmokeTest T10 只测"能入队/有响应"，未验证基因真的改变，故漏检。
   - 修复：`to_upper().replace(".", "_")` 或显式映射；补 T10 断言——调用后验证代表基因组 trait 真变化。
   - 风险：低（仅命令名映射）；触及 Agent 契约但**不改接口名**，只修内部映射，不破坏冻结契约。

**P1 — 机制层缺口（需评估是否真缺）**
2. **§5.3.6「细胞器 / 表达型」双层语义**：v1.1 把 v1.0 的 16 种功能细胞重新解释为"细胞器模块"，运行时每细胞的"表达型"应是细胞器权重向量（显示名），而非枚举常量。当前 `Genome.gd` 仍是 traits + cell_type 枚举；"细胞器"只见于渲染层（`CellView.gd` 的 `organelle_root` 是视觉多边形）。**需确认**：这是文档术语统一（不影响玩法）还是必须落地的机制（表达预算、重复装备税）。若属后者，触及 GNP1 冻结边界，必须先走 v1.0 修订流程。
3. **§5.3.6 重复装备税 / 培养基导出基础值**：最小自治核基础值应由培养基营养密度导出（皿级只读标量、进存档），"单细胞策略付重复装备税"的可观察中间状态未见实现证据。属玩法机制缺口，需先确认优先级与是否冻结。

**P2 — 表现层缺口（v1.1 明确标注"表现层可先行实现"）**
4. **§3.3.1 显微视野控制**：镜头滤镜切换、视野旋转、视野锁定、图层图例、三类缩略图捕获——v1.1 增补清单，代码里未见明确实现（grep 仅命中 `AnalysisPanel`/`GenomePreview` 等泛用词，无专门控件）。
5. **§4.3.1 实验条件档位 / §4.3.2 无渲染快进**：与方向一的倍速 LOD 缺口（1.2 节）重叠，一并处理。
6. **§7.5 培养基设置**：培养基预设与环境自定义的完整 UI。

### 2.3 执行步骤

1. **先修 P0 bug**：`AgentBridge` 命令名映射 + T10 补断言（验证 trait 实际变化）。过双工程 SmokeTest + NativeParityProbe（此改动不进 hash，仅命令路由）。这是唯一可直接动手、无需先确认方向的项。
2. **再确认 P1 属性**：读 §5.3.6 + `Genome.gd` + `DevelopmentRules.gd`，判断"细胞器/表达型"是术语统一还是机制缺口。**若要落地机制，先走 v1.0 修订**（§0.3 / §10.3 流程），不直接改 GNP1。
3. **P2 表现层**：按 v1.1 明确清单逐项做，每项验收 = 视觉/交互可观察 + 不写模拟状态 + 不进 hash。
